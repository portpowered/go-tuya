# Template migration checklist: go-tuya

Source: `go-third-party-template/docs/library-standards.md` and its release
and verification guides. Sign-off records below are specific to this library.

- [x] **1.** Keep the public client, examples, README, and site independent of any consuming application. Put application adapters and rollout plans in the consuming repository. **Signed off:** package, examples, README, and authored guides contain no backend adapter or rollout instructions. The documentation sources are provider-library focused.
- [x] **2.** Document supported operations, authentication, errors, and transport injection with examples that match the exported API. Add customer-facing operation guides for important workflows, and distinguish verified behavior from synthetic examples and historical references. **Signed off:** README and authentication, device, events, testing, and provider notes cover the public surface; the auth example uses the exported methods. Documentation labels replay fixtures as synthetic and separately records the maintainer's report of successful real-account testing, noting that sanitized captures and route-by-route provenance were not recorded.
- [x] **3.** Show Go version, CI, coverage, release, Go Reference, license, and documentation badges in the README. Replace every example repository value and point badges to live reports. **Signed off:** all seven badges use this repository/module. CI and Docs passed; the Pages coverage report and badge data returned HTTP 200 and report 38.4% combined coverage. The `v0.1.0` tag triggered a successful release workflow: version/API compatibility, build, race, vet, replay, and a fresh consumer fetch through `proxy.golang.org` passed before the GitHub Release was published. The release and Go Reference badges returned HTTP 200, the release badge displayed `v0.1.0`, and the versioned Go Reference page returned HTTP 200. In an isolated local clone, the later-release compatibility command passed against a temporary `v0.1.0` baseline using Go 1.26 for apidiff.
- [x] **4.** Generate the API reference in CI with the shared Fumadocs action and publish it to GitHub Pages. Keep schemas checked in and reviewed, generate schema-defined Go models from them, and check for stale generated output in CI. Publish authored Markdown or MDX operation guides alongside the reference. Replace the template's clearly synthetic widget schema before presenting a provider API as supported behavior. **Signed off for the documented scope:** `api/openapi.yaml` covers the officially documented `GET /v1.0/devices` subset; pinned generation produces an internal response model used by `QueryDevices`, and the Docs workflow checks for drift. The shared Fumadocs action built and deployed successfully; the published guide and route reference returned HTTP 200. The maintainer reports successful real-account testing of the implemented flows, but no sanitized exchanges or route-by-route provenance were recorded. The private `/v1.0/m/...`, MQTT, RTC, and encrypted transport contracts remain outside the provider schema and are not presented as matching official wire specifications.
- [x] **5.** Run offline build, lint, race, and replay checks before release. Keep real captures sanitized and separate from synthetic fixtures. **Signed off:** after the v0.2.0 package, client/session, and transport work, `make lint`, `make check` (build and race tests), and `make replay` passed. Replay fixtures remain explicitly synthetic with neighboring provenance notes; the maintainer's real-account test report remains undocumented and is not represented as captured evidence.
- [x] **6.** Generate synthetic data to target higher test coverage. Reach at least 80% statement coverage across non-generated package code, aiming for 90%, and enforce the 80% floor in CI. Keep generated models out of the metric and keep synthetic cases separate from captured behavior. **Signed off:** `make coverage` passes at 81.4% (1,101/1,352) on non-generated package statements. The Make, CI, and docs workflows profile only `./pkg/...` and apply the same 80% floor; generated models are excluded, and synthetic route/session/message-queue cases are distinct from provider captures. The 90% target remains a stretch goal.
- [x] **7.** Ensure package shape is `pkg/<library>` with provider wire types under `pkg/<library>/internal/wire`. **Signed off:** public API source and tests are under `pkg/tuya`; generated wire schema and model files are under `pkg/tuya/internal/wire`. Root examples and the published Go Reference import `github.com/portpowered/go-tuya/pkg/tuya`.
- [x] **8.** Ensure client initialization uses options for base configuration inputs. **Signed off:** `NewClient(options ...Option)` validates required HTTP transport, client ID, endpoint URLs, MQTT factory, and options; `WithRegion`, endpoint, HTTP, MQTT, and RTC options are exercised by synthetic tests.
- [x] **9.** Ensure the client is stateless; lift stateful operations into a session object. **Signed off:** `Client` stores reusable configuration and `Client.NewSession` creates independent token and message-queue state. Synthetic tests verify token changes in one session do not affect another.
- [x] **10.** Ensure the HTTP client or over-the-wire client is injectable, including HTTP/2, WebSocket, or other network-edge transports. **Signed off:** `WithHTTPClient` and `WithHTTPTransport` inject HTTP for auth, cloud requests, and default HTTP RTC signaling; `WithMQTTClientFactory` injects MQTT client creation; `WithRTCSignaling` accepts an alternate signaling client such as a WebSocket implementation. Synthetic tests exercise the HTTP RoundTripper, MQTT factory, RTC seam, and existing HTTP RTC flow.
- [x] **11.** Ensure token refresh is not opaque and callers can retrieve their own tokens. **Signed off:** `Session.Tokens` reads a snapshot, `Session.SetTokens` explicitly replaces credentials, and `AuthService.RefreshToken` returns rotated values without mutating the session. A synthetic refresh test verifies the request and return values and proves the session remains unchanged until the caller applies the new pair.
