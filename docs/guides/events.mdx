# Events

Each account session owns a `MessageQueue`. Register a listener, start the
queue, and stop it when the listener's lifetime ends. Handle events without
logging complete payloads, which can contain device identifiers and state.

```go
queue := session.MessageQueue
_, err := queue.AddDeviceListener(ctx, tuya.AddDeviceListenerRequest{
    DeviceID: deviceID,
    Callback: func(_ string, event tuya.Event) {
        switch event.(type) {
        case *tuya.DeviceStateChangeEvent:
            // Handle a state change.
        case *tuya.DeviceManagementEvent:
            // Handle a management event.
        }
    },
})
if err != nil {
    return err
}

if _, err := queue.Start(ctx, tuya.MessageQueueStartRequest{}); err != nil {
    return err
}
defer queue.Stop(context.Background(), tuya.MessageQueueStopRequest{})
```

`Start` connects before returning and reports initial connection errors. For
later connection failures, read `queue.Status()`; its `Connected` and
`LastError` fields show the current state. `Stop` waits for the queue loop to
exit and disconnects the broker. The session owns that queue state. Event
callbacks run synchronously and serially without an unbounded goroutine queue;
a slow callback delays later MQTT message delivery. Keep callbacks short or
move work into an application-managed bounded queue.

The parser handles device-state protocol 4 and device-management protocol 20
messages. Unknown management codes remain generic management events. This
implementation-derived event support is not a complete Tuya event catalog.

The built-in client subscribes over MQTT to owner and device status topics
supplied by Tuya's message queue configuration. It does not provide a
WebSocket event connection.

See the generated references for [owner events](../../asyncapi/message-events/receiveOwnerEvents)
and [device status events](../../asyncapi/message-events/receiveDeviceStatus).
